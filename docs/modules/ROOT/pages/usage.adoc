= Usage

include::includes/attributes.adoc[]

Everything starts from the `Libvips` bean (package `org.sitenetsoft.quarkus.libvips`), a thread-safe singleton:

[source,java]
----
@Inject
Libvips libvips;
----

== Images

`Libvips.load` and `Libvips.thumbnail` return an `Image`, a handle on a libvips image. Images are immutable: every
transform returns a new `Image` and leaves its source open.

*Close every image*, with try-with-resources. `close()` is idempotent and thread-safe; any use after it throws
`IllegalStateException`. A derived image keeps what it needs alive inside libvips, so closing its source first is
safe. An image that is never closed is released by a `Cleaner` once it is unreachable and counted in
`Libvips.leakedImages()`; that is a safety net, not a way to manage memory: the native memory stays allocated until
the garbage collector runs. `Libvips.openImages()` counts the images open now.

[source,java]
----
byte[] squareJpeg(byte[] upload) {
    try (Image image = libvips.load(upload);
            Image upright = image.autorotate();
            Image square = upright.smartCrop(600, 600, Interesting.ATTENTION)) {
        return square.save(SaveOptions.jpeg(85));
    }
}
----

=== Loading

`load(byte[])` and `load(Path)` read only the header; pixels are decoded when an operation needs them. A damaged file
can therefore load fine and fail later, in `save` or `thumbnail`, with a `LibvipsException` naming that operation;
the images involved stay valid and closable.

[source,java]
----
try (Image image = libvips.load(upload)) {
    int width = image.width();
    int height = image.height();
    int orientation = image.orientation();     // 1 to 8, from EXIF; 1 when there is none
    String loader = image.loader();            // "jpegload_buffer"
    Optional<byte[]> icc = image.iccProfile();
    Map<String, String> exif = image.exif();   // parsed tags by field name
    Optional<String> make = image.field("exif-ifd0-Make");
}
----

`LoadOptions` selects the access pattern, the `fail_on` level for this load (else `quarkus.libvips.fail-on`) and the
pages of a multi-page image:

[source,java]
----
LoadOptions strict = new LoadOptions(Access.SEQUENTIAL, Optional.of(FailOn.TRUNCATED), 0, 1);
try (Image image = libvips.load(file, strict)) {
    // ...
}
----

A file is opened by its exact name: a trailing `[...]` is never read as libvips loader options. Names that end in
white space or are longer than 4093 bytes are refused, and so is anything that is not a regular file (a FIFO, device
or directory). Every load goes through the limits and blocked operations of xref:security.adoc[Security and limits].

Input arrays are copied to native memory once, into a blob libvips owns. That copy of the whole input stays in
native memory for as long as the `Image` (or an image derived from it) refers to it, and, if you turn the operation
cache on, for as long as cached operations do (see xref:configuration.adoc#operation-cache[The operation cache]).
The extension's own loads are never cached. Format detection copies at most the first 64 KiB.

=== Thumbnails

[source,java]
----
// fit inside 800 wide, never enlarge (the default)
try (Image a = libvips.thumbnail(upload, 800, ThumbnailOptions.DEFAULT)) { }
// fill 300 x 300, cropping to the most interesting part
try (Image b = libvips.thumbnail(upload, 300, ThumbnailOptions.box(300, Interesting.ATTENTION))) { }
// fit inside 800 x 600 and convert to sRGB
ThumbnailOptions fit = new ThumbnailOptions(OptionalInt.of(600), Size.DOWN, Interesting.NONE, false,
        Optional.of("srgb"), Intent.RELATIVE);
try (Image c = libvips.thumbnail(upload, 800, fit)) { }
----

A thumbnail is turned upright by its EXIF orientation unless `noRotate` is set.

* `Libvips.thumbnail(byte[], …)` is the fast path for uploads: libvips shrinks while decoding where the format allows
  (JPEG, WebP, HEIF, PDF, SVG). With a pixel limit set, the header is read once on its own first, so the full size is
  checked before any pixel is decoded.
* `Libvips.thumbnail(Path, …)` loads the file through the loader its content selects and reduces it with
  `thumbnail_image`: there is *no* shrink-on-load (libvips's own file thumbnail reads loader options from a `[...]` at
  the end of the name, so it is not used). For large JPEGs, read the file into memory and use the `byte[]` method.
* `Image.thumbnail(…)` works on an image already loaded, also without shrink-on-load.

To size by height alone, give the height and a width as large as the height argument allows (10 000 000 works on every
supported libvips).

=== Transforms

[source,java]
----
try (Image half = image.resize(0.5);
        Image corner = image.crop(0, 0, 100, 100);
        Image srgb = image.iccTransform("srgb", Intent.PERCEPTUAL)) {
    // ...
}
----

`autorotate()`, `thumbnail`, `resize`, `crop`, `smartCrop`, `iccImport()` and `iccTransform` cover the common cases.
Colour profiles are a built-in name (`srgb`, `sgrey`, `p3`, `cmyk`) or the absolute path of a regular ICC file; take
such a path from the application's configuration, never from request data (see
xref:security.adoc#file-name-arguments[File-name arguments]).

=== Saving

[source,java]
----
byte[] jpeg = upright.save(SaveOptions.jpeg(85));
byte[] png = upright.save(SaveOptions.png());
byte[] webp = upright.save(new SaveOptions.Webp(90, true, 6, Set.of(Keep.ICC, Keep.EXIF)));
byte[] avif = upright.save(SaveOptions.avif(50));
byte[] gif = upright.save(SaveOptions.gif());
----

Each `SaveOptions` record names its libvips saver (`jpegsave_buffer`, `pngsave_buffer`, `webpsave_buffer`,
`heifsave_buffer` with AV1 compression for AVIF, and `gifsave_buffer` for GIF); savers are never looked up by suffix.

[cols="1,2,3"]
|===
|Record |Saver |Settings (factory values)

|`Jpeg` |`jpegsave_buffer` |quality 1–100, interlace (progressive), keep (`jpeg(q)`: not interlaced, ICC)
|`Png` |`pngsave_buffer` |compression 0–9, interlace (Adam7), keep (`png()`: 6, not interlaced, ICC)
|`Webp` |`webpsave_buffer` |quality 1–100, lossless, effort 0–6, keep (`webp(q)`: lossy, 4, ICC)
|`Avif` |`heifsave_buffer` |quality 1–100, lossless, effort 0–9, keep (`avif(q)`: lossy, 4, ICC)
|`Gif` |`gifsave_buffer` |effort 1–10, bitdepth 1–8, interlace, keep (`gif()`: 7, 8 bits, not interlaced, nothing)
|===

GIF needs libvips built with cgif (Ubuntu 24.04's `libvips42t64` is; `hasOperation("gifsave_buffer")` tells);
`bitdepth` caps the palette at 2^bitdepth^ colours (8: 256). A default load (and a thumbnail) reads only the first
page, so an animated GIF is saved as its first frame; load it with `pages` = `-1` to keep every frame.

[IMPORTANT]
.Turn images upright before saving
====
The factories (`jpeg`, `png`, `webp`, `avif`) keep only the ICC profile (`Set.of(Keep.ICC)`) and strip the rest of
the metadata. That drops the EXIF block, and with it the orientation: a photo that was not turned upright saves
sideways as JPEG, PNG or WebP. GIF has no orientation at all, so it always saves the pixels as they are. Call
`autorotate()`, or make a thumbnail (which turns it upright), before saving. AVIF records the rotation in its
container (`irot`) and keeps it.
====

`Keep` mirrors libvips's `VipsForeignKeep` flags `EXIF`, `XMP`, `IPTC`, `ICC` and `OTHER`; an empty set keeps nothing.
libvips 8.18 also has a gain-map flag that `Keep` does not expose, so gain maps are always dropped. `OTHER` is
libvips's "other" class (such as PNG text chunks), not everything the other flags leave out.

A saver that exists but cannot encode (blocked, or AVIF without libheif's AV1 encoder plugin) fails with a
`LibvipsException` naming it; a saver this libvips does not have at all is an `UnsupportedFormatException` with
reason `NO_SAVER`.

== Any libvips operation

`Image.call` runs any libvips operation on an image, for what the typed methods do not cover:

[source,java]
----
Image sharpen(Image image) {
    return image.call("sharpen", Map.of("sigma", 1.5));
}
----

The image goes into the operation's image input (`in`, or `input` for operations such as `extract_area`) unless the
map names one; other `Image` values in the map are passed as images. Values: `Integer`, any `Number` for doubles,
`Boolean`, `String`, enums as the extension's enums (`Interesting`, `Intent`, …) or their libvips nick, flags as
`Integer` bits or a nick such as `"icc:exif"`, `byte[]` for blobs and `double[]` for arrays of doubles. Every argument
is checked against the operation's parameter specification before anything runs: an unknown, output, deprecated or
out-of-range argument is an `IllegalArgumentException`. The operation must return its image as `out`; loaders and
savers (use `load` and `save`), operations that modify an image in place (`draw_*`), and `system`, `globalbalance` and
`remosaic` are refused.

== Discovery

[source,java]
----
Optional<String> loaderClass = libvips.loaderFor(upload); // "VipsForeignLoadJpegBuffer"
Optional<String> saverClass = libvips.saverFor(".webp");  // "VipsForeignSaveWebpBuffer"
boolean avif = libvips.hasOperation("heifsave_buffer");
boolean blocked = libvips.isBlocked("ppmload");
----

* `isBlocked` takes a nickname (`ppmload`) or a *concrete* class name (`VipsForeignLoadPpmFile`); an abstract class
  name such as `VipsForeignLoadPpm`, which the block lists accept, throws `IllegalArgumentException`: ask about a
  concrete variant.

* `loaderFor` and `saverFor` return GType *class names*; `Image.loader()` returns the loader's *nickname*
  (`jpegload_buffer`).
* `saverFor` is a suffix lookup only: `.avif` finds nothing, because libvips's HEIF saver declares `.heic` and `.heif`.
  `save` does not use it. `saveSuffixes()` lists every suffix some saver accepts.
* `hasOperation` tells whether this libvips was built with an optional format; an encoder plugin missing from libheif
  does not show there.
* `status()` returns the version, library, effective settings and counters (what the health check reports); it never
  throws. Its `library()` is the value libvips was opened by and may be a host path: the health check shows only its
  file name.

[[threads]]
== Threads

`Libvips` is thread-safe. An `Image` may be read and transformed from several threads at once. Closing an image while
another thread uses it is a bug in the caller, but a safe one: the other thread's next call throws
`IllegalStateException`, and the native image is released only when the last call using it returns.

[[event-loops]]
=== Event loops

libvips decodes, transforms and encodes on the calling thread, and a large upload takes tens of milliseconds to
seconds. The methods that do that work refuse to run on a Vert.x event loop (an I/O thread), the way Quarkus's own
blocking APIs (Hibernate ORM's session, for one) do: they throw Quarkus's `BlockingOperationNotAllowedException`
naming the method, before libvips is called. That covers `Libvips.load`, `loaderFor`, `thumbnail`, and on `Image`
`call`, `autorotate`, `thumbnail`, `resize`, `crop`, `smartCrop`, `iccImport`, `iccTransform` and `save`.

What only reads state runs anywhere: the `Image` header reads (`width()` to `iccProfile()`), `close()`, and on
`Libvips` `isAvailable()`, `version()`, `library()`, `status()` (the health check), the counters, `hasOperation`,
`isBlocked`, `saverFor` and `saveSuffixes`.

Run image work on the worker pool:

* Quarkus REST: an endpoint that returns a plain value (`byte[]`, `Response`, an entity) already runs on a worker
  thread. One that returns `Uni` or `Multi`, or a reactive route, runs on the event loop: annotate it with
  `@Blocking`.
* Vert.x code: `vertx.executeBlocking(() -> ...)`.
* Mutiny: switch the pipeline before the call with `emitOn(Infrastructure.getDefaultWorkerPool())`, or wrap the call
  with `Uni.createFrom().item(() -> ...).runSubscriptionOn(Infrastructure.getDefaultWorkerPool())`.

Virtual threads (`@RunOnVirtualThread`) are allowed but not recommended for this: a libvips call is a native call,
which pins the virtual thread to its carrier thread for the whole call, and image work is CPU-bound and can take
seconds, so a few large uploads would hold every carrier. The worker pool is sized for blocking work.

[source,java]
----
@POST
@Path("/thumbnail")
@Blocking // the method returns a Uni, so it would otherwise run on the event loop
public Uni<byte[]> thumbnail(byte[] upload) {
    try (Image thumbnail = libvips.thumbnail(upload, 800, ThumbnailOptions.DEFAULT)) {
        return Uni.createFrom().item(thumbnail.save(SaveOptions.webp(80)));
    }
}
----

Outside a Quarkus application (plain unit tests) every thread may block and nothing is refused.

=== libvips worker threads

libvips also runs its own worker threads inside each pipeline: `quarkus.libvips.concurrency` sets how many (libvips's
default is the `VIPS_CONCURRENCY` environment variable, else one per processor). On a server handling many uploads at
once, a small value (2 to 4) keeps one large image from taking every core.

== Errors

All exceptions are unchecked and extend `LibvipsException`, whose `operation()` names the libvips operation that
failed:

[cols="1,3"]
|===
|Exception |When

|`LimitExceededException`
|The input is larger than `limits.max-input-size`, or its header declares more pixels than `limits.max-input-pixels`;
`actual()` and `limit()` give the numbers. Thrown before any pixel is decoded. Also an output larger than a Java byte
array can hold (about 2 GiB, `operation()` `output-size`), refused before it is copied.

|`UnsupportedFormatException`
|`NO_LOADER`: no loader accepts the input (empty, unknown or blocked format, or a missing file). `NO_SAVER`: this
libvips has no such saver.

|`LibvipsUnavailableException`
|libvips could not be loaded (with `required=false`), or the application is shutting down.

|`LibvipsException`
|The operation failed, for example a damaged image when its pixels are computed.
|===

[source,java]
----
byte[] safeThumbnail(byte[] upload) {
    try (Image thumbnail = libvips.thumbnail(upload, 800, ThumbnailOptions.DEFAULT)) {
        return thumbnail.save(SaveOptions.webp(80));
    } catch (LimitExceededException e) {
        throw new IllegalArgumentException("image too large: " + e.actual() + " > " + e.limit(), e);
    } catch (UnsupportedFormatException e) {
        throw new IllegalArgumentException("not an image we accept", e);
    } catch (LibvipsException e) {
        throw new IllegalArgumentException("could not process the image (" + e.operation() + ")", e);
    }
}
----

A call on a Vert.x event loop throws Quarkus's `BlockingOperationNotAllowedException` instead (see
<<event-loops>>); it is not a `LibvipsException`.

Exception messages are fixed text naming the operation and the kind of failure. `detail()` carries libvips's error
text, for logs only: it can name host paths and is best-effort under concurrency, so never return it to a client (see
xref:security.adoc#errors-under-concurrency[Errors under concurrency]). Invalid arguments (out-of-range sizes or
qualities, a closed image) are `IllegalArgumentException` and `IllegalStateException`, thrown before libvips runs.

[[leak-check]]
== Leak check

To find images that are never closed, or memory libvips keeps, set `quarkus.libvips.leak-check=true` in dev or test
mode (for example `%test.quarkus.libvips.leak-check=true`, and run the whole test suite). libvips then runs its own
leak checks (`vips_leak_set`), and when the application stops the extension logs one line: INFO
`libvips leak check: no leaks; ...` when everything was released, else a WARN with the images still open, the images
the cleaner released because they were never closed, and the pixel memory and files libvips still tracks. libvips
lists any of its objects still alive on standard error. In production the key is ignored with a warning: the checks
cost time and the report is a diagnostic. Tests of the packaged application (`@QuarkusIntegrationTest`, a native
image) start in production mode; to check them, also set `quarkus.libvips.leak-check-in-production=true` for those
runs only.

Once on, libvips keeps checking until the JVM exits, even after a dev-mode restart or a later test application
without the key: libvips cannot switch its own checks off safely while images from the checked period may still be
alive. Only the extension's report follows the key. Set it for a whole dev session or test run.
